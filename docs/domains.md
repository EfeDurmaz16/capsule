# Domain References

Capsule models runtime as distinct domains so provider differences stay visible. This document details each domain and how the real adapters behave. For the high-level split see [Architecture](architecture.md); for declared support levels see the [Capability model](capability-model.md) and [Provider matrix](provider-matrix.md).

## Sandbox

A sandbox is a bounded execution workspace. Capsule models creation, command execution, file reads and writes, file listing, upload/download, logs, artifacts, port exposure, snapshots, workspace mounts, and destruction. Provider categories include local Docker containers, E2B sandboxes, Daytona workspaces, Modal sandboxes, Cloudflare Sandbox, Microsandbox, and future Firecracker or microVM adapters.

Policy concerns include network access, filesystem boundaries, secret injection, output redaction, timeout, CPU, memory, and artifact collection. Capsule can validate and record policy decisions, but the actual isolation strength depends on the provider. Docker local is useful for development and CI, but it is not safe for hostile untrusted code unless configured carefully outside Capsule. Capsule will not claim OS-level isolation when it is only invoking Docker CLI.

**Docker.** Sandbox sub-operations are governed through the core wrapper: `exec`, `writeFile`, `readFile`, `listFiles`, and `destroy` each run with their own capability check, policy decision, and receipt scope when used through `Capsule`. Requested `exposedPorts` map to Docker `--publish` flags bound to `127.0.0.1` by default, so published ports are local-only unless the caller supplies another `hostIp`; this does not turn Docker into a remote service provider and does not bypass `network.none`. Snapshot and restore are explicitly unsupported: Capsule exposes no public restore API and does not model portable restore semantics, filesystem consistency, running-process state, or policy/audit continuity, so `sandbox.snapshot` and `sandbox.restore` stay unsupported until implemented as public operations with tests.

**E2B.** Uses the official E2B SDK for creation, command execution, file read/write/list, and destruction. Network `none` maps to E2B's internet-access control; host allowlists and OS-level filesystem policy remain provider-specific or adapter-boundary concerns. If creation succeeds but a later local step fails (receipt signing, persistence preflight), Capsule attempts to kill the allocated sandbox and attaches cleanup metadata to the thrown error. If command execution throws before returning an exit code, Capsule conservatively kills the sandbox and records whether cleanup was killed or failed. Normal nonzero exits are returned as `sandbox.exec` results and do not trigger destruction.

**Daytona.** Uses the official Daytona TypeScript SDK for creation, command execution, file read/write/list, and deletion. `network.none` maps to Daytona network blocking and `allowlist` to Daytona's network allow list; filesystem policy stays adapter-boundary enforcement. Cleanup-on-failure mirrors E2B, using Daytona delete. Cleanup is best-effort because provider-side delete can fail during outages or credential revocation, so interrupted live runs should be checked in the Daytona console before rerunning.

**Modal.** Uses the Modal JavaScript SDK for creation, command execution, file read/write, and termination. Modal's public sandbox file listing surface is not a stable high-level method, so `sandbox.fileList` remains unsupported rather than faked. Create receipts include app, environment, image, and requested network metadata; exec receipts record text-mode metadata such as workdir and timeout; destroy receipts are written only after `terminate()` succeeds, so terminate failures propagate instead of producing a misleading deleted receipt.

Live integration tests for E2B, Daytona, and Modal are opt-in and skipped unless both `CAPSULE_LIVE_TESTS=1` and the provider API key are set. Do not set `CAPSULE_LIVE_TESTS=1` in routine local or CI runs unless live provider operations are intended.

## Jobs And Services

Capsule separates deployment domains instead of flattening them. Jobs cover finite work: Cloud Run Jobs, ECS tasks, Kubernetes Jobs, Lambda, Modal functions, Docker one-off containers, and Azure Container Apps Jobs. Services cover long-running HTTP or TCP workloads: Cloud Run Services, ECS/Fargate Services, Kubernetes Deployments and Services, Azure Container Apps, Fly Apps, Railway, Render, and Docker Compose-style local dev. Cloud Run, ECS, and Kubernetes overlap naturally for both.

**Cloud Run.** Uses the Cloud Run Admin API v2. It creates and runs jobs, maps execution `completionStatus` from the Execution API for `job.status`, sends execution `:cancel` for `job.cancel`, creates services from container images, waits for long-running operations when configured, and records receipts. Execution deletion is intentionally separate from cancel: deleting an execution removes the execution resource/list entry and is exposed only through the provider client helper. Service update uses `services.patch` with revision-producing template updates; service rollback is a full 100% traffic move to one revision, and partial traffic splits are rejected until Capsule models split-release state explicitly. Job/service logs are bounded reads through Cloud Logging `entries:list`. The adapter does not fake stdout/stderr, mutate IAM to make services public, or deploy from source through Cloud Build.

**Kubernetes.** Uses the official Kubernetes JavaScript client. It creates Jobs for `job.run` and a Deployment plus Service for `service.deploy`; service status reads both resources, service delete removes both, and URLs prefer assigned LoadBalancer ingress before falling back to in-cluster DNS. Job and service logs are native when a Job or Service selector can identify Pods; Capsule reads combined Pod logs without alpha split-stream parameters and rejects follow-mode streaming until bounded streaming is modeled. It does not claim rollout completion, ingress exposure, RBAC enforcement, or runtime isolation beyond what the cluster provides.

**Lambda.** Maps `job.run` to invoking an existing Lambda function through AWS SDK v3. It is not a function deployment adapter yet: Capsule passes command/env/image metadata as event payload and records the invoke response, but does not update function code, mutate environment variables, or provision API Gateway/Lambda@Edge. Invoke receipts include request ids, requested qualifier, executed version, log type, and parsed log-tail request id when available.

**ECS/Fargate.** Maps `job.run` to `RunTask` and `service.deploy` to `CreateService` through AWS SDK v3. It requires an existing task definition and explicit cluster/container/network options, records the intended image, but does not register task definitions, create load balancers, provision IAM roles, or configure CloudWatch Logs yet. If `CreateService` succeeds and a later step fails, Capsule best-effort deletes the created Service and attaches cleanup metadata to the thrown error.

**Azure Container Apps.** Maps `service.deploy`, `service.status`, and `service.delete` to ARM Container App create/update, get, and delete; managed environment, ingress, registry, identity, secrets, revisions, and scaling stay visible in specs and metadata. `job.run` performs a manual Container Apps Job create/update followed by the ARM job start, reads state through the ARM job execution resource, and maps `job.cancel` to the ARM stop-execution operation. Cancel is execution-only and does not delete the Job resource; generated jobs are deleted only when `job.run` creates a temporary Job and start fails before returning. ARM exposes revision activate/deactivate, but Capsule does not expose a generic service rollback in this adapter. It does not yet stream Log Analytics output or collect artifacts.

## Edge

Edge deployment is separate from service deployment because global runtime platforms expose different concerns. Vercel centers on deployments, functions, routes, builds, aliases, releases, and framework integration. Cloudflare centers on Workers, Pages, bindings, routes, Durable Objects, KV, R2, D1, and Containers. Lambda can behave like job/function execution or edge-adjacent function deployment depending on API Gateway, Lambda@Edge, or routing setup. Capsule models edge deploy, version creation, release, rollback, routes, env, bindings, logs, URL discovery, and receipts, and expects provider-specific escape hatches.

**Cloudflare.** Implements a narrow Workers subset: `edge.deploy` uploads a Worker module with multipart metadata to the Workers Scripts API, creates zone-scoped Workers routes when `routes` and `zoneId` are provided, and optionally returns a workers.dev URL when configured with a known subdomain. `edge.version` uploads a Workers version without releasing traffic. `edge.rollback` creates a Workers Deployment with 100% traffic to a selected version and requires `providerOptions.scriptName` plus either `targetVersionId` or enough Deployments history to infer the previous version. It does not create secrets, provision KV/R2/D1/Durable Objects, read logs, or manage gradual traffic-split releases. Provider-specific and secret `bindings` remain unsupported; plain text `env` values are uploaded as Worker vars.

**Vercel.** Creates deployments through the Vercel REST API using inline files in the create request, appropriate for small examples and control-plane contract testing. It reads deployment event logs and project runtime logs when a project id is provided; follow-mode log streaming is rejected until Capsule has bounded streaming semantics, and release traffic splits other than 100% are rejected. Larger applications should use Vercel's file upload/SHA flow; domains, environment variables, route management, and rollback are intentionally separate future capabilities.

## Database And Resource

Database resources are deployment-adjacent runtime state. Neon branches are the first model: create a branch from a parent, expose a connection string, optionally run migrations, reset, snapshot, restore, delete, and emit a resource receipt. Preview environments often need temporary database branches, so Capsule makes branch TTL, cleanup, migration logs, connection string handling, and receipts explicit. Connection strings are sensitive: adapters should avoid logging them, and examples should print them only when explicitly safe or fake.

Reset and migration are optional capabilities: `database.branchReset` is exposed as `capsule.database.branch.reset(...)` and `database.migrate` as `capsule.database.migrate(...)`. Adapters must declare unsupported until they implement the operation. The Neon adapter supports branch create/delete, connection URI retrieval, and branch reset through Neon's branch restore API. Migration remains unsupported because Capsule does not yet define a provider-safe migration runner.

## Machine

Machines include EC2, GCP Compute Engine, Azure VM, bare metal, Firecracker, Nomad, and lower-level Fly Machines. They are leakier than sandboxes, jobs, services, or edge deployments: image formats, disks, networking, firewall rules, identity, SSH, startup scripts, regions, placement, snapshots, and cleanup differ substantially. Use the machine primitive when the user needs lower-level control, and do not hide provider-specific security, networking, volume, or lifecycle details behind false portability. The core facade models create, status, start, stop, and destroy as separate capabilities, and adapters must mark each honestly because VM lifecycle APIs differ in state transitions, billing, termination protection, data persistence, and network identity.

**EC2.** Implements machine creation through `RunInstances` and lifecycle through `DescribeInstances`, `StartInstances`, `StopInstances`, and `TerminateInstances`. It creates one instance from an AMI and instance type with optional subnet, security groups, key, IAM profile, tags, and user data. `machine.destroy({ force: true })` forwards EC2 `Force`, `providerOptions.skipOsShutdown` forwards EC2 `SkipOsShutdown`, and both are recorded in receipt metadata because they affect shutdown safety; destroy records current and previous states and fails if EC2 does not return termination state. Capsule does not hide SSH, patching, IAM, network exposure, disk lifecycle, startup script security, or teardown. Job/service wrappers, exec, and snapshot remain unsupported until modeled explicitly.

**Fly.** Maps Fly Machines to machine lifecycle operations through the Fly Machines API. `job.run` creates an auto-destroy Machine with restart policy `no`; log streaming, exit-code waiting, volumes, services, and Fly App networking are intentionally separate future capabilities.
