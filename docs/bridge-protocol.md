# Fabric bridge protocol

Capsule can run as a provider worker for [Fabric](https://github.com/EfeDurmaz16/fabric), a durable job runner. Fabric spawns the worker as a local child process and sends it one governed provider action at a time over framed stdio. This page is a pointer. The specification lives in Fabric and is the single source of truth:

- Specification: Fabric `docs/bridge-protocol.md` (bridge protocol v1).
- Decision record: Fabric `docs/adr/0021-capsule-provider-bridge.md`, adopting drafts P09 (scoped provider identity and truthful outcomes) and P10 (Capsule worker protocol) as Proposed.
- Reconciliation: Fabric `docs/adr/0022-reconciliation-and-cleanup-authorization.md`, adopting draft P11 (unknown outcomes, reconciliation and cleanup authorization) as Proposed, and the specification's section "Reconciliation (M4)".

Status: proposed, 2026-10-27; amended 2026-10-29 (an exec bound of 0 is invalid; an observe carries the original operation's scope; both profiles observe an exec; fixture seeds carry the operation label); amended again 2026-10-29 by Fabric ADR 0022 for M4 (the `attach` message; see "Reconciliation (M4)" below); corrected 2026-11-03 (a locator without a `native_id`, the profile's `max_timeout_ms`, an observe that finds no resource answers `absent`; see "Corrections of 2026-11-03" below). The worker is implemented in [`@capsule-sdk/bridge-worker`](../packages/bridge-worker) and passes every shared fixture, M4's included. It is not released yet.

## What Capsule owns

| Concern                                                                                | Owner          |
| -------------------------------------------------------------------------------------- | -------------- |
| Job, task, attempt and operation identity, the operation journal, placement, fencing   | Fabric         |
| Provider mapping, provider calls and observations, receipts, Capsule policy evaluation | Capsule worker |

The worker keeps no durable job state. A worker restart is transport loss, never cancellation, and never a reason to retry an action.

## Rules that touch existing Capsule types

- The wire locator is Capsule's `ResourceLocator` in snake case: `provider`, `scope`, `kind`, `native_id`, optional `native_operation_id`. Every effect and result carries it.
- A terminal-only action that does not reach a terminal state within its deadline answers `pending` with the locator, last state, observation count and deadline, the shape of `PendingOperationError`. An action whose effect cannot be known answers `unknown` with the best known locator, the shape of `UnknownOutcomeError`.
- Refusals (`invalid`, `unsupported`, `denied`, `unavailable`) happen before any provider call and carry `effect: "none"`.
- Fresh per-operation approval is additive: it never overrides a policy deny, and a create grant never authorizes destroy.
- A present secrets block with omitted `allowed` denies all secrets; two allowlists merge by intersection.

## Fixtures

`protocol/bridge/v1` in this repository is a byte-identical copy of Fabric's `protocol/bridge/v1`: framed byte cases, message cases, scenarios for the deterministic fixture provider, and the v1 capability profiles for the fixture provider and local Docker. `scripts/bridge-fixtures.test.mjs` checks every file against `manifest.sha256` and pins the manifest's own sha256; Fabric pins the same digest. Never edit these files in one repository alone: a change lands byte for byte in both, with the pin, in linked pull requests. Fabric's text stays the source of truth; the 2026-10-29 fixtures for observe scope, exec observe and seed operation labels, and the 2026-11-03 corrections below, were written here and copied to Fabric. Until v1 first ships, a correction goes into v1 this way rather than into a v2 (the specification's Versioning section). Prettier ignores the directory so its bytes stay exact.

## Corrections of 2026-11-03

Three corrections to v1, decided on 2026-11-02 by the implementation agent under Efe's delegation of that day (recorded so, not as approved by Efe), with their fixtures written here and copied to Fabric:

- A request `target` or observe `resource` whose `native_id` is absent, null or empty names no resource and is `invalid`/`missing_field`; it was `bad_locator`, the reason for a malformed id. Only a `sandbox.create`, which carries no locator, has no resource yet. A worker frame with such a locator is `protocol_violation`/`missing_field`. A worker approval grant with an empty `native_id` is refused at config time; `null` stays the form of a grant not tied to one resource, which a Docker destroy needs because its container id exists only after the create (cases `request_destroy_null_native_id`, `request_exec_null_native_id`, `request_exec_empty_native_id`).
- Both profiles advertise `max_timeout_ms` in `limits` (fixture 60000, docker 3600000): the bound of an exec's own `timeout_ms`, which may exceed `max_deadline_ms` since an exec still running at its request deadline is answered `running` and observed. A `timeout_ms` above it is `invalid`/`limit`, as a `max_output_bytes` above the profile's 1 MiB already was; that bound keeps two streams of one exec answer inside one 16 MiB frame (cases `request_exec_timeout_above_profile`, `request_exec_output_above_profile`; the profiles, `hello_ack_valid` and the two scenarios that embed a `hello_ack` carry the field).
- An observe whose one read finds no resource in the bound scope answers `unknown`/`absent` with `effect: "unknown"`, `observations: 1`, `deadline_ms` (the `wait_ms`) and the `searched` scope, for a `sandbox.create` and a `sandbox.destroy` alike (an exec's outcome is in the exec ledger, so an exec observe is unchanged); it answered `provider_failed`/`not_found` for a create and `result completed`/`destroyed` for a destroy. What absence settles is Fabric's journal's to say: a destroy's resource gone is the destroy done, with the searched scope on the row; a create's may still land, so the create stays `unknown`. A destroy the provider answers `not_found` is a bare `not_found` and settles nothing by itself; Fabric observes the destroy by its operation and target, and the absent answer settles it. `searched` is required on `unknown`/`absent` and refused on every other error, `not_found` among them; the worker keeps no ledger of earlier reads (cases `error_not_found_with_searched`, `error_provider_refused_with_searched`, both refusals; scenarios `destroy_not_found_settles_on_absent_observe` and `pending_destroy_with_locator`, whose last observe now finds the resource gone).

## Reconciliation (M4)

Fabric's specification, section "Reconciliation (M4)", is the source of truth; this is what it asks of the worker. Reconciliation only reads: Fabric never sends a request again, and the worker never retries one.

- `attach` finds the resource an earlier create of an operation made, by that operation's identity, for an operation whose answer never reached Fabric. It carries `operation_id`, `key`, the original `scope`, the original `action` and `wait_ms`, and never a resource. It is supported for exactly the actions whose profile `effect` is `create` and whose `dedupe` is `provider_key` or `label_query`: `sandbox.create` in both profiles. Any other action in the profile is `unsupported`/`attach`.
- The worker looks for the resource with the driver's `findCreated` at each observe interval until `wait_ms`, reads its labels before it reports anything (another job, or another operation, is `denied`/`owner_mismatch`), then observes it as an observe of the action does. Answers: `completed` with the locator; `pending`/`observation_deadline` with the locator when it is found but not terminal; `unknown`/`absent` with `searched` (the profile's provider, the worker's bound scope and the resource kind) when nothing carries the operation's identity; `unknown`/`observation_failed` when a read fails. Absence settles nothing: a Docker create may still land after its worker ended.
- A cleanup is an ordinary destroy with a fresh grant scoped to `sandbox.destroy` on that resource; nothing changes in the worker for it.
- The fixture provider accepts a seed sandbox with `status: "starting"`, which is not terminal for a create and becomes `ready` at `advance: settle`.
- A scenario may carry a `journal_state` header for Fabric's journal; the worker's scenario run ignores it.
- An observe of a create or a destroy reads the resource once before anything else is reported; when that read finds nothing in the bound scope it answers `unknown`/`absent` with the scope searched (see "Corrections of 2026-11-03"). A read that finds the resource runs the owner checks, then observes it to a terminal state within `wait_ms`: a destroy whose resource goes away during that wait answers `result completed`/`destroyed`, a create that reaches ready answers `result completed`/`ready`.

How the worker answers an attach, beyond the specification's text:

- A look is `findCreated` and, when it names a resource, one read of it; the owner check runs on that read, and later looks only read the found resource. A resource found but already gone counts as not found. `observations` counts the looks that finished, so a look still in the docker CLI at `wait_ms` is not counted, and the answer still comes at `wait_ms`.
- An attach never answers `provider_failed`, since it makes no effect that could fail: a binding that cannot be read (`docker context show`) or a look that fails is `unknown`/`observation_failed`, with the locator once a resource was found.
- An attach counts against `max_in_flight` like an observe, a cancel of it is acknowledged `unsupported`, and at `shutdown` it is answered `pending`/`shutting_down` with the locator when found, else `absent` with the looks made, and listed in the ack's `unresolved`.

## The worker

`@capsule-sdk/bridge-worker` ships the `capsule-bridge-worker` bin. One process serves one capability profile:

```sh
pnpm build
node packages/bridge-worker/dist/bin.js --profile fixture --config worker.json
node packages/bridge-worker/dist/bin.js --profile docker --config worker.json --receipts receipts.jsonl
```

Installed from npm the same command is `capsule-bridge-worker --profile <fixture|docker> --config <file>`. The config holds the scope the worker is bound to (`binding`), the worker's policy (`images`, `secrets.allowed`) and the approval grants it can resolve by ref (`approvals`); a scenario's `provider_state` is a valid fixture config. For Docker, `binding.engine` names a docker context, and every docker command the worker runs names it with `--context=`, so the engine scope on a locator is the engine the command reaches. `binding` may be omitted; the scope is then read once from `docker context show` and kept, even if the CLI's current context changes later.

The worker also builds as one executable that needs no Node, Bun or pnpm on the host, a Node single executable application: `pnpm build && pnpm bridge:sea` bundles the bin the package ships and runs `node --build-sea`, so the build needs Node 25.5 or later (Node 26 LTS; Node 22 and 24 would need a separate injector) and the executable embeds that Node. It is built for the platform it is built on, and signed ad hoc on macOS. `pnpm bridge:artifact-smoke` copies it to a fresh directory, runs it with an empty PATH, and replays every shared scenario, the refused frame fixtures and SIGTERM and SIGINT over its stdio. The CI job `bridge-artifact` does both on Linux x64.

How the worker applies the protocol:

- Checks run in a fixed order and stop at the first failure, all before any provider call: frame, JSON, message schema, action in profile, locator scope, idempotency, owner, policy (images, secrets), fresh approval. Then the request goes through the Capsule facade, which checks policy and the grant again before the adapter runs. Idempotency is checked before policy, because the shared scenario `duplicate_idempotency_key` expects a conflict for a changed request that policy would also refuse; the specification lists the same order.
- The idempotency table holds up to 4096 keys and at most 16 Mi characters of exec output across its answers. Past that the oldest answers are dropped and only their key and digest stay, so a repeat of such a key is refused as `idempotency_conflict` and never runs again. Fabric never repeats a key, so this costs it nothing.
- An observe names the original operation's `scope` (`job`, `task`, `attempt`, `generation`, under the request's rules); one without it is `invalid`/`missing_field`. The worker reads the resource's labels before it reports anything: a resource another job made, or no job, is refused as `denied`/`owner_mismatch` for every action, so a destroy observe never settles on another job's resource. A create observe also needs the resource's operation label to be the observing operation; a resource with this job's label alone is refused. A fixture seed (`sandboxes[]`) that names `owner_job` carries `operation` too, as every container the Docker profile creates carries both labels, and the fixture provider refuses a seed with one and not the other. Every effect the fixture provider records carries the operation id it was made for.
- An observe of `sandbox.exec` is answered from the worker's exec ledger, which holds every exec this worker process sent, by operation id: the exec's own `completed` or `cancelled` result once the command ended (with its output, `replayed: false`), `pending`/`observation_deadline` with `state: "running"` while it runs past `wait_ms`, and `unknown`/`observation_failed` with the locator for an exec this process did not send or no longer holds. A ledger record names the exec's sandbox and job, and an observe naming another is `denied`/`owner_mismatch`. Nothing runs the command again. The ledger is bounded like the idempotency table: at most 1024 records and 16 Mi characters of output text in ended records, oldest ended record dropped first; a running record is never dropped. It does not survive the worker, so an exec answered `running` before a worker loss is `unknown` to the next worker.
- A residual scan is part of the worker's internal API, not of v1: `listResiduals(driver, { operations, jobs })` lists what carries the profile's operation label in the bound scope (Docker: `docker ps` by `fabric.operation`; fixture: its seeded and created sandboxes) and splits it by the live sets Fabric holds. It changes nothing. Removal stays `sandbox.destroy` with a fresh approval, observed gone. A v1 message for the scan waits until Fabric mirrors its fixtures, since the fixture manifest is pinned in both repositories.
- An existing resource is reached with `Capsule.sandbox.attach`, which changes nothing and carries no create grant, so exec and destroy are governed per operation.
- A grant resolved from an approval ref is scoped to exactly that action, and to that resource when the grant names one. A ref is per operation: once it has resolved for one operation id, the same ref on any other operation is `denied`/`approval_scope` for the rest of the worker's life, so a retry of that operation may carry it again and nothing else can. The ref never reaches receipts or logs.
- Secret values are read only for names the worker's own policy allows, at the execution boundary. Docker reads them from the worker's environment; nothing else does.
- The fixture profile runs on a virtual clock: each observation advances 1000 ms, so deadlines and observation counts are exact on any host. Docker uses the wall clock with 250 ms between observations. On the wall clock every wait ends at `deadline_ms` after the frame was read (`wait_ms` for an observe), so no answer comes after Fabric's own deadline: checks still reading then are refused before any effect (`provider_failed`/`provider_refused`); a create or destroy still in the docker CLI is answered `unknown` with the best locator, for a create the container name the worker gave it, which an observe by the original operation id resolves (and a `docker start` the CLI timeout kills afterwards leaves the container in place: the adapter reports it unknown by id and never removes a container it could not see start, so a sandbox Fabric holds by then is not destroyed without a destroy); an observation read still in flight is answered `pending`; and an exec is answered `running`, and an observe of its operation later reports how it ended. A provider can also accept an exec and run it on by itself; the worker then answers `running` at once (the fixture's `run_until_settle` does this, and its command ends at the next `advance: settle`). Work that goes on after its answer keeps counting against `max_in_flight` until it ends.
- The parser refuses exactly what the specification refuses. An exec `timeout_ms` or `max_output_bytes` of 0 is `invalid`/`limit`, a rule the specification and the shared cases `request_exec_timeout_zero` and `request_exec_output_bytes_zero` carry since 2026-10-29; Fabric refuses the same request before sending it. A request label in the `fabric.` namespace is overwritten by the worker's own labels, so it cannot claim another owner. Values a provider cannot take safely are refused by that profile before any call: the Docker profile refuses an image or container id that starts with a dash and a label key that holds `=`, because each becomes a docker CLI argument.
- The Docker profile creates with `--pull never`, labels each container `fabric.operation`, `fabric.job`, `fabric.attempt` and `fabric.generation`, refuses a container without this job's label, and finds an earlier create of the same operation by label after a worker restart instead of creating another.
- Losing stdin is a shutdown with a 0 ms drain and SIGTERM one with 5 s; open requests are answered pending or unknown, nothing is cancelled at the provider, and the process exits 0. A framing error or a refused hello exits 2. When the session ends, the Docker profile kills any `docker exec` client still attached, so no CLI process outlives the worker; the command keeps running in the container. A worker killed with SIGKILL cannot do this; Fabric, which starts the worker as the leader of a process group, ends that group when it loses the worker, and an exec client and the reads (`context`, `version`, `ps`, `inspect`, `cp` out of a container) are in it. Clients of create, start and rm are left to finish, because killing one could abort the daemon's work: each starts in a process group of its own (`detached` in `runDocker`), so neither the end of the session nor a signal to the worker's group reaches it, as the specification requires of any process whose end would end or abort an effect.

Evidence: `packages/bridge-worker/src/*.test.ts` run all 24 scenarios, 58 cases and 15 frames and check that every refusal left the fixture provider's effect log empty; `attach.test.ts` proves that a create whose answer died with its worker is attached by the next worker and never made again, and that its cleanup is refused without a fresh destroy grant before any effect, and `docker.test.ts` proves the same attach by operation label on the Docker profile; the pack smoke runs the packed bin outside the repository; `pnpm bridge:docker-smoke` proves the Docker profile on a local engine, and the CI job `bridge-docker-smoke` runs it with `--require` on a digest-pinned busybox the job pulls first; `benchmarks/after/bridge` holds spawn and round-trip measurements with raw data. From the other side, Fabric's `crates/fabric-bridge/tests/capsule_worker.rs` spawns this worker, replays every shared scenario over its stdio with Fabric's own framing and parser, and runs Fabric's client and journal against the fixture and Docker profiles, M4's lost create, lost destroy and unsent create included; `benchmarks/after/bridge/fabric-client` holds that run's raw timings, and `benchmarks/after/bridge/m4-reconcile` the M4 runs (the Node worker and the executable, each with and without the engine), this worker's artifact and Docker smokes and its gates.
